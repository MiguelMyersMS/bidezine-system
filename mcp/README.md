# The Sandbox MCP server

Milestone 3 of [the Sandbox](../docs/SANDBOX-SPEC.md). How agents reach the corpus.

## Both clients, one server

Standard MCP over stdio. Nothing here is Claude-specific, and it is registered for both:

| Client | Config |
|---|---|
| Claude Code | [`.mcp.json`](../.mcp.json) → `sandbox` |
| GitHub Copilot | [`.vscode/mcp.json`](../.vscode/mcp.json) → `sandbox` |

Both point at the same `mcp/server.mjs`. A change to a tool reaches both clients at once,
and neither can do something the other cannot — which matters, because the guarantees
below are the point of the whole system and would be worthless if one client could
sidestep them.

Copilot also reads [`.github/copilot-instructions.md`](../.github/copilot-instructions.md),
which carries the same protocol summary Claude gets from `CLAUDE.md`. Skills under
`.claude/` are Claude Code-only and do not transfer; anything that must apply to both
belongs in the MCP server or in those two instruction files.

## What it solves

Storing decisions was never the hard part. Getting the *right three* into a session's
context at the moment they matter is.

`CLAUDE.md` is the evidence: roughly 15,000 words that every session pays for in full,
most of it irrelevant to whatever is actually being worked on. `sandbox_decisions`
replaces that for anything already decided — ask what the project has concluded about
scroll gutters and get three rows back, not fifteen thousand words.

## The credential

**The server connects as `agent_rw`, always.** That role cannot insert evidence, cannot
set state, and cannot approve — enforced by database permissions (`db/migrations/002`),
proven live by `db/verify-invariant.mjs`.

If a tool here ever needs more power than `agent_rw` has, that is a signal the design is
wrong, not a reason to hand the server a stronger credential.

## Tools

| Tool | What it is for |
|---|---|
| `sandbox_decisions` | **Start here.** Search resolved decisions by category or keyword, before proposing any value. |
| `sandbox_categories` | The fixed category enum. Adding one is a migration, not a call-time choice. |
| `sandbox_components` | Components, states, owning machine, divergence counts. |
| `sandbox_divergence` | One divergence in full: rationale, evidence with raw output, reviews, gate status. |
| `sandbox_gate` | The unmet-requirement list. Your to-do list, generated by the thing that will refuse you. |
| `sandbox_propose_divergence` | File a proposal. Lands as `proposed`, never as done. |
| `sandbox_update_divergence` | Revise rationale, category, anchor. Not state — state is not yours. |
| `sandbox_submit_review` | An independent verdict, citing evidence by id. |
| `sandbox_reopen` | Record that something marked resolved was never actually finished. |
| `sandbox_how_to_verify` | Why you cannot write evidence, and what to do instead. |

Tool descriptions are deliberately long. They are the only place an agent learns the
protocol before acting, and a one-line description would mean every agent rediscovers
the rules by hitting refusals.

## Two behaviours worth knowing

**A refusal returns the database's own words.** The server does not flatten a permission
error into a generic failure — the agent should see exactly what it may not do, and be
told plainly not to look for another credential.

**`evidence_id` is a `BIGINT`, which the driver returns as a string.** `sandbox_submit_review`
therefore accepts numbers *and* numeric strings for `cites`. This was a real bug caught by
`verify-mcp.mjs`: the server emitted string ids from `sandbox_divergence` and then rejected
those same ids when cited back, so no review could ever have cited evidence read through
the server.

## Verify

```bash
npm --prefix mcp run verify   # 14/14
```

Talks to the real server over stdio, exactly as the clients do, against the live database.
It does not import the server's functions — that would test the code while skipping the
protocol, the transport and the credential, which is where things actually break.
