# CLARIFICATIONS — RailNav

DS-side answers to consumer gap-requests for `RailNav` (protocol §5/§9). Read this **before** rebuilding.
Round 1 findings were verified by the DS side against the deployers' actual committed/exported files and the
component code — not the chat reports.

## Round 1 answers (Copilot + Claude Design)

### CD1.1 — Default has no single overflow state (viewport-dependent burial) — CLARIFIED
**Verified real.** `Organisms/RailNav → Default` is `layout:"fullscreen"` with a `100dvh` wrapper and no
pinned rail height, so with 16 sections the burial threshold (~834px) means a tall window shows 16-on-rail and
a shorter one shows 12 + "More". An embedded replica needs a bounded height.
**Answer:** for an embedded Default replica, use the assembled-frame reference height **730px** (`railnav.spec.md`
`container.height: 730`) — it yields the canonical **12 sections + "More"** lineup (`Emailing` + trailing
sections buried), matching `FigmaSpec`. Claude Design's disclosed 730px choice is **correct — accepted**.
Overflow is viewport-derived by design; the 730px reference is the canonical embedded state. (§4B will name it.)

### CD1.2 / CD0.6 — utility slot could not be built from the bundle — FIXED
**Verified real.** The root barrel `src/index.ts` was a hand-maintained allow-list that had drifted from
`src/gallery/index.ts` and omitted the rail sub-atoms; the UMD entry (`export * from "./index"`) inherited the
omission, so `window.DS` exposed no `RailButton`/`RailButtonDark` (only `RailNav`/`IconLogo`). Claude Design
correctly transcribed the story's utility button and disclosed it — not a fork.
**Answer (fixed, PR #63):** `RailButton`, `RailButtonDark`, `LogoSlot`, `LogoSlotDark` (+ their types) are now
exported from the package root and the `window.DS` bundle. After the next bundle re-export, compose the utility
slot from the atom: `utilityItems={<DS.RailButtonDark section={{ id:"profile", label:"Profile", icon: DS.IconPerson }} disabled />}`.
Also **`utilityItems`/`footer` are a `React.ReactNode` slot, not an array of descriptors** (the plural name
misleads — passing `[{id,label,icon,onClick}]` throws); documented in `railnav.spec.md` FooterSlot mode 2.

### CD1.3 — no prop-surface docs reach a browser consumer — FIXED
**Verified real.** `dist-browser/` shipped only the bundle + manifest + consumption README; the spec is Figma
anatomy and the behavior contract cites `src/` line numbers — no `.d.ts`, no props table.
**Answer (fixed, PR #63):** `dist-browser/API.md` now ships a generated prop/type reference for every
`window.DS` component (name · required · type · JSDoc), regenerated by `build:umd`. RailNav's entry documents
`defaultExpandedGroups`, `panelTitle`, the aria/label defaults, and the full surface. After the next re-export
you will have `dist-browser/API.md` — read it instead of `src/`.

## New capabilities landed for this round (PR #63)

- **Leaf nav** — a section with no `items` is now a **direct nav button** (fires `onNavigate(id, id)`), not a

## What each path must do

**RAW-TS PATH (`ADIAS-dashboard`)** — re-pull the package so your install carries the change
(`npm install`/update against `github:miguelmyers/design-system@master`), re-render the view, and confirm

**BROWSER-BUNDLE PATH (`ds-docs-site`)** — re-ingest `dist-browser/` from `master` and re-run the pin
gate. `window.DS.version` must equal `master`'s `ds-manifest.json` `version`; assert against the repo

**How to verify it rather than eyeball it** — 13px/500 vs 14px/400 is a small difference and easy to
"see" either way. Read the computed style instead:

```js
getComputedStyle(el)  // expect fontSize "13px", fontWeight "500", lineHeight "18.2px"
```

`18.2px = 13 × 1.4`; if you get a round `13px` line-height the token did not resolve.

## Why you are being told rather than left to find it
